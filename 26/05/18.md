# Part 1: Boris Cherny 直伝：Claude Code の開発フロー

なぜか奈良に住んでたことがあるらしい Claude Code を作った Boris Cherny が、実際にどう Claude Code を使っているかをまとめたドキュメント。一次情報のみを根拠としています（個人ブログや AI 生成記事は除外）。

   <https://www.threads.com/@boris_cherny/post/DUMZr4VElyb>
2. Pragmatic Engineer インタビュー「Building Claude Code with Boris Cherny」（2026年3月）

5. Anthropic 公式「Best practices for Claude Code」
   <https://code.claude.com/docs/en/best-practices>

## 前提：Boris Cherny とは

- Anthropic の Staff Engineer
- **Claude Code を作った本人**
- 1 日に **20〜30 個の PR** を送る
- 設定は「驚くほどバニラ」と本人が公言（複雑な仕様書フレームワークも凝った MCP も使っていない）

> 「私のセットアップは驚くほどバニラかもしれない。Claude Code はそのままで素晴らしく動くので、個人的にはあまりカスタマイズしない」— Boris Cherny

## 中核ワークフロー

```
[Plan Mode] → [Auto-accept Edits] → [Verification]
   計画         一気に実装           検証・テスト
       ↑                              ↓
       └── 失敗したら戻る ─────────────┘

並列で 10〜15 セッションを常時稼働
       ↓
CLAUDE.md にチーム知識を蓄積（PR レビュー時に @claude タグで追記）
       ↓
頻出作業は Slash Command 化して git で共有
```

## ステップ別解説

### ステップ 1：Plan Mode で必ず始める

これが Boris の **最重要原則**。

> 「PR を書く時は Plan mode を使い、Claude と計画について納得いくまで往復する。気に入ったら auto-accept edits モードに切り替えて、Claude は大抵 1 回で実装してくれる。良い計画は本当に重要」— Boris Cherny

**起動方法**：
- 通常モードで Claude Code を起動 → `Shift + Tab` を 2 回押す
- または最初から plan mode で起動

**Boris チームの裏技**：
- 1 つの Claude に計画を書かせて、**別の Claude を起動して「スタッフエンジニアの視点でレビューさせる」**
- 実装中に何かおかしくなった瞬間に **Plan Mode に戻って再計画する。強行突破はしない**

### ステップ 2：Auto-accept Edits で一気に実装

計画が固まったら、確認のたびに止まらず流す。

> 「Plan Mode は補助輪じゃない。切る前に測るのと同じだ。一貫して ship できる開発者は計画を飛ばさない。苦労している人ほど時間節約のために計画を飛ばし、結局ミスの修正に時間を使う」

### ステップ 3：Verification（検証）— 公式が「最重要」と呼ぶもの

ここが Boris の哲学の核心。

> 「Claude Code から素晴らしい結果を得るためにおそらく最も重要なこと：Claude に自分の作業を検証する手段を与える。そのフィードバックループがあれば、最終結果の品質は 2〜3 倍になる」— Boris Cherny

**具体的に何をやっているか**：

- ユニットテスト
- E2E テスト（Chrome 拡張機能でブラウザ操作）
- スクリーンショット比較
- ビルド・型チェック・lint

> 「Claude は私が claude.ai/code に送る全ての変更を、Claude Chrome 拡張機能を使ってテストする。ブラウザを開き、UI をテストし、コードが動いて UX が良いと感じられるまで反復する」

これらを**最初から仕込んでおく**のが Boris のやり方。

### ステップ 4：CLAUDE.md にチームで知識を蓄積

Boris チーム独自の運用。

> 「Claude Code リポジトリでは、チーム全体で 1 つの CLAUDE.md を git に登録して共有している。チーム全員が週に何度も貢献する」

**黄金ルール**：

> 「Claude が何か間違ったことをしたら、その都度 CLAUDE.md に追加する。次回から Claude がその間違いをしないように」

つまり CLAUDE.md は「最初に完璧に書く」のではなく、**「Claude のミスを毎回記録して育てる」もの**。

**サイズ感**：
- Boris チームの CLAUDE.md は **約 2.5K トークン**
- これより大きいと逆効果（Claude が指示を無視し始める）

**PR レビューを通じた更新**：
- Boris は同僚の PR に `@claude` をタグして、学びを CLAUDE.md に追加する
- **コードレビューが「将来の AI への教育」になっている**
- これがチーム運用の肝

### ステップ 5：頻出作業は Slash Command に

> 「1 日に複数回行うことは、skill または slash command にする。コマンドは git に保存して共有する」

Boris 自身は `/commit-push-pr` を 1 日に何十回も使う。

`.claude/commands/` ディレクトリに置いて git 管理。**チーム全員が同じコマンドを使える**。

**裏技**：
- コマンドに inline bash を含めて、`git status` などのコンテキストを事前計算
- モデルとの往復を減らせる

## 並列セッション運用 — Boris の真骨頂

「20〜30 PR/日」を可能にしている部分。

### 構成

- **ターミナルで 5 つの Claude Code** を同時実行
  - タブを 1〜5 で番号付け
  - システム通知でどの Claude が入力待ちか分かるようにする
  - **各タブは別の git checkout** を使う（ブランチでも worktree でもなく、別チェックアウト）
- **claude.ai/code 上で 5〜10 セッション**を追加で動かす
- 合計 **10〜15 セッションが常時稼働**

### Boris の考え方

> 「Boris は AI を『使うツール』ではなく『スケジュールするキャパシティ』として捉えている。計算リソースのように認知を分散させている：割り当て、キューに入れ、温かく保ち、価値が準備できた時にだけコンテキストスイッチする」

## 重要：「PRD は死んだ」

Anthropic 内部の認識として最も重要なポイント。

> 「Claude Code チームでは、PRD（製品要求仕様書）は死んだ：プロトタイプが取って代わった」— Pragmatic Engineer インタビュー

**Anthropic 社内の Claude Code チーム自体が、もう仕様書を書かずにプロトタイプから始めている**。

外部が「Spec-Driven Development」と騒いでいる一方で、開発元の中の人はもっとシンプルにやっている。

## モデル選択：常に Opus の推論モード

> 「Boris はあらゆるタスクに Opus 4.5 の思考モードを使う。理由：『これは私が今まで使った中で最高のコーディングモデル。Sonnet より大きく遅いが、ステアリングが少なくて済み、ツール使用が上手いので、結局小さいモデルを使うより速い』」

**「速いモデルを使う」より「ステアリングが少なくて済むモデルを使う」**という発想。

## Boris 流チャレンジテクニック

Claude に対する高度な指示パターン。

**a) Claude をレビュアー役にする**
> 「この変更について私を問い詰めて。あなたのテストに合格するまで PR は作らないで」

**b) 中途半端な実装をリセットさせる**
> 「今知っていることを全て踏まえて、これを破棄してエレガントな解法を実装して」

**c) 渡す前に詳細仕様を書く**
> 「仕事を渡す前に詳細な仕様を書いて曖昧さを減らす。具体的であるほど良い出力が得られる」

## Boris が **やっていない** こと

「巷で流行っている手法」のうち、Boris が使っていないもの：

- ❌ Spec-Kit、Kiro、BMAD などの仕様駆動開発フレームワーク
- ❌ MCP 連携を大量に詰め込む
- ❌ 凝ったプロンプトテンプレート
- ❌ 詳細な事前仕様書（PRD・SRS・SAD・ERD など）
- ❌ `--dangerously-skip-permissions`（代わりに `/permissions` で安全コマンドを事前許可）

> 「驚くべきは彼のセットアップの中身ではない。何が **入っていない** かだ。エキゾチックなカスタマイズはない、巧妙なハックもない。基本を規律正しく適用しているだけ」

## まとめ：Boris 哲学を 1 文で

> **「重い事前準備ではなく、軽い計画 → 一気に実装 → 強い検証ループ。学びは CLAUDE.md に蓄積。1 人で並列に動く」**

これが Claude Code を作った本人の使い方。

## 付録：CLAUDE.md の実例（Anthropic Claude Code リポジトリ）

Boris チームが実際に使っている CLAUDE.md の冒頭部分（公開済み）：

```markdown
# Development Workflow

**Always use `bun`, not `npm`.**

# 1. Make changes
# 2. Typecheck (fast)
bun run typecheck
# 3. Run tests
bun run test -- -t "test name"       # Single suite
bun run test:file -- "glob"          # Specific files
# 4. ...
```

ポイント：
- 短い
- Bash コマンドを明示（Claude が推測できないもの）
- 「これをしないとミスする」という具体的な指示のみ

# Part 2: Anthropic 公式：Extend Claude Code

Claude Code を使いこなすための 6 つの拡張機能（CLAUDE.md、Skills、MCP、Subagents、Hooks、Plugins）の使い分けガイド。Anthropic 公式「Extend Claude Code」ページの内容をもとに日本語で整理したもの。

## 出典

- Anthropic 公式「Extend Claude Code」
  <https://code.claude.com/docs/en/features-overview>
- Anthropic 公式「Best practices for Claude Code」
  <https://code.claude.com/docs/en/best-practices>

## 結論：何から始めるか

**新規ユーザーは CLAUDE.md だけから始めれば良い**。他は必要になった時点で追加する。

公式の言葉：

> 「Claude Code が初めてなら、まずプロジェクトの規約を CLAUDE.md に書くところから始めて、具体的なトリガーが現れた時点で他の拡張機能を追加していけば良い」

## 全体像：6 つの拡張機能

| 機能          | 役割                                           | いつ使うか                                         |
| ------------- | ---------------------------------------------- | -------------------------------------------------- |
| **CLAUDE.md** | 毎セッション自動で読まれる持続的なコンテキスト | プロジェクト規約、「常に X せよ」のルール          |
| **Skills**    | Claude が使える再利用可能な知識やワークフロー  | 再利用したい内容、参照ドキュメント、繰り返しタスク |
| **MCP**       | Claude を外部サービスに接続するプロトコル      | 外部のデータやアクションが必要なとき               |
| **Subagents** | 隔離されたコンテキストで動く別の Claude        | コンテキストの隔離、並列タスク、専門ワーカー       |
| **Hooks**     | イベント発火時に実行される決定的なスクリプト   | LLM を使わない予測可能な自動化                     |
| **Plugins**   | 上記をまとめて配布するパッケージ               | 複数リポジトリで同じセットアップを再利用           |

## 追加していく順番（公式推奨）

下記のトリガーが現れた時に、対応する機能を追加する：

| トリガー                                                | 追加するもの                                   |
| ------------------------------------------------------- | ---------------------------------------------- |
| Claude が同じ間違いを 2 回した                          | CLAUDE.md に追記                               |
| 同じプロンプトを何度も打ち直している                    | Skill として保存（`/コマンド名` で呼び出せる） |
| 同じ手順書を 3 回目チャットに貼り付けた                 | Skill として保存                               |
| Claude が見えないブラウザタブからデータをコピーしている | MCP サーバーとして接続                         |
| 後で参照しない大量の出力で会話が埋まる                  | Subagent に作業を回す                          |
| 毎回確認なしで実行したい処理がある                      | Hook を書く                                    |
| 同じセットアップを別のリポジトリでも使いたい            | Plugin としてパッケージ化                      |

## CLAUDE.md

### 何か

**毎セッション自動で読み込まれる Markdown ファイル**。プロジェクトの規約や「常に X せよ」を書く。

### 置き場所

- `~/.claude/CLAUDE.md`（全プロジェクト共通）
- プロジェクトルートの `./CLAUDE.md`（チーム共有、git 管理）
- `./CLAUDE.local.md`（個人用、.gitignore に入れる）
- サブディレクトリ（モノレポで便利）

### サイズの目安

**200 行以下** に保つ。それを超えたら参照資料は Skill に切り出す。

Boris チームの CLAUDE.md は約 2.5K トークン（≒ 200 行程度）。

### 中身の原則

**「これを削除したら Claude が間違えるか？」と毎行に問う。答えが No なら削る。**

入れるべきもの：

- Claude が推測できない Bash コマンド
- デフォルトと違うコードスタイル
- テストの実行方法
- リポジトリのマナー（ブランチ命名等）
- プロジェクト固有のアーキテクチャ決定
- よくあるハマりどころ

入れてはいけないもの：

- コードを読めば分かること
- 標準的な言語慣習
- 詳細な API ドキュメント（リンクで十分）
- 頻繁に変わる情報
- 「きれいなコードを書け」のような自明な原則

### 重要な運用ルール

**「Claude が何か間違えたら、その都度 CLAUDE.md に追記する」**。これが Boris チームの黄金ルール。

## Skills

### 何か

**Claude が使える再利用可能な知識やワークフロー**。Markdown ファイル + frontmatter で定義する。

`/コマンド名` で手動呼び出しもできるし、Claude が文脈から判断して自動ロードもする。

### 置き場所

- `.claude/skills/skill-name/SKILL.md`(プロジェクト用)
- `~/.claude/skills/skill-name/SKILL.md`(個人用)

ディレクトリ構造になっているのは、関連ファイル（テンプレート、リファレンス資料など）も同じフォルダに置けるから。

### 最小例

`.claude/skills/api-conventions/SKILL.md`:

```markdown
---
name: api-conventions
description: REST API 設計規約
---

# API 規約

- URL パスは kebab-case
- JSON プロパティは camelCase
- リスト系エンドポイントは必ずページネーション
- API は URL パスでバージョニング（/v1/, /v2/）
```

### ワークフロー型の例

`.claude/skills/deploy/SKILL.md`:

```markdown
---
name: deploy
description: 本番環境にデプロイする
disable-model-invocation: true
---

以下の手順でデプロイしてください：

1. すべてのテストが通っているか確認
2. `npm run build` でビルド
3. ステージング環境にデプロイ
4. スモークテスト実行
5. 本番デプロイ
6. Application Insights でエラー監視

各ステップで失敗したら止まって私に報告すること。
```

### `disable-model-invocation: true` の意味

**Claude には見えなくなり、`/deploy` で手動呼び出し専用になる**。副作用のある操作（デプロイ、ファイル削除など）には必ず付ける。

### CLAUDE.md との使い分け

|                  | CLAUDE.md        | Skill                            |
| ---------------- | ---------------- | -------------------------------- |
| ロードタイミング | 毎セッション自動 | オンデマンド                     |
| ワークフロー起動 | できない         | `/<name>` でできる               |
| 用途             | 「常に X」ルール | 参照資料、呼び出し型ワークフロー |

**ルール**：CLAUDE.md は 200 行以下。それを超えたら Skill に分割する。

### 重要：旧 slash command との関係

以前は `.claude/commands/xxx.md` で slash command を作っていたが、**現在は Skills に統合された**。両方とも `/コマンド名` で呼び出せるが、**新規作成は Skills 形式が推奨**。既存の `.claude/commands/` のファイルは変更なしで動き続ける。

## MCP（Model Context Protocol）

### 何か

**Claude を外部サービスに接続するプロトコル**。データベース、Slack、Figma、Notion、ブラウザ等への接続を可能にする。

### 何ができるか

- データベースに直接クエリ
- Slack にメッセージ投稿
- Figma のデザインを参照
- Notion の社内ドキュメントを読む
- ブラウザを操作

### セットアップ

```
claude mcp add <server-name>
```

公式マーケットプレイス：<https://claude.com/partners/mcp>

### コスト

- セッション開始時：ツール名だけがロード（軽量）
- 実際に使うとき：完全なスキーマがロード

`/mcp` コマンドで現在の MCP サーバーのトークンコストを確認できる。**使っていないサーバーは切断するべき**。

### 注意点

**MCP 接続はセッション中に静かに切れることがある**。サーバーが切断されると、警告なしでツールが消える。Claude が以前は使えていた MCP ツールを使えなくなったら、`/mcp` で接続状態を確認する。

### MCP と Skill の組み合わせ

これが重要なパターン：

- **MCP**：外部システムへの接続そのもの
- **Skill**：その MCP をどう使うかの知識

例：

- MCP がデータベースに接続する
- Skill が「データモデル」「よく使うクエリパターン」「どのタスクでどのテーブルを使うか」を教える

両方揃って初めて Claude が外部システムを「上手に」使える。

## Subagents（サブエージェント）

### 何か

**メインの会話とは独立した、隔離されたコンテキストで動く別の Claude**。作業結果のサマリーだけメインに返ってくる。

### 何が嬉しいか

- メインのコンテキストが汚れない
- 大量のファイルを読む調査タスクを丸投げできる
- 並列実行できる
- 専門化したワーカーを作れる

### 置き場所

`.claude/agents/agent-name.md`(プロジェクト用)
`~/.claude/agents/agent-name.md`(個人用)

### 例：セキュリティレビュアー

`.claude/agents/security-reviewer.md`:

```markdown
---
name: security-reviewer
description: コードのセキュリティ脆弱性をレビューする
tools: Read, Grep, Glob, Bash
model: opus
---

あなたはシニアセキュリティエンジニアです。以下の観点でコードをレビューしてください：

- インジェクション脆弱性（SQL、XSS、コマンドインジェクション）
- 認証・認可の欠陥
- ハードコードされた秘密情報や認証情報
- 安全でないデータ処理

具体的な行番号と修正案を示すこと。
```

### 呼び出し方

> "Use a subagent to review this code for security issues."

### Subagent と Agent teams の違い

|                    | Subagent                     | Agent team                        |
| ------------------ | ---------------------------- | --------------------------------- |
| 通信               | メインの Claude にだけ報告   | メンバー同士が直接やりとり        |
| コーディネーション | メインの Claude が管理       | 共有タスクリストで自己組織化      |
| トークンコスト     | 低（サマリーだけ返る）       | 高（各メンバーが独立した Claude） |
| 用途               | 結果だけ欲しい焦点的なタスク | 議論や協調が必要な複雑な作業      |

Subagent で足りなくなったら Agent team を検討する。

## Hooks（フック）

### 何か

**イベント発火時に自動実行されるスクリプト**。LLM は介在しない、決定的な処理。

### CLAUDE.md と何が違うか

CLAUDE.md の指示は **アドバイザリ**（Claude が従うかは判断による）。Hook は **決定的**（必ず実行される）。

### 例

- ファイル編集後に必ず ESLint を走らせる
- migrations フォルダへの書き込みをブロック
- Claude の応答後にコードを自動フォーマット
- 重要ファイルが変更されたら Slack 通知

### Boris チームの例

Boris は **PostToolUse Hook で Claude のコードを自動フォーマット** している。Claude は大体フォーマット済みのコードを書くが、最後の 10% を Hook で潰すことで CI 失敗を防ぐ。

### 設定場所

`.claude/settings.json` を直接編集するか、`/hooks` で確認・編集。

Claude に Hook を書かせることもできる：

> "Write a hook that runs eslint after every file edit"
> "Write a hook that blocks writes to the migrations folder"

## Plugins（プラグイン）

### 何か

**Skills、Hooks、Subagents、MCP サーバーを 1 つのインストール可能なユニットにまとめたもの**。

### 何が嬉しいか

- 同じセットアップを複数リポジトリで再利用
- マーケットプレイス経由で他人と共有
- Skills の名前衝突を回避（プラグインは namespace 付き：`/my-plugin:review`）

### 使い方

```
/plugin    # マーケットプレイスを開く
```

公式マーケットプレイスや、Anthropic 提供のプラグインから選んでインストールできる。

## 機能の重ね合わせ（公式の典型パターン）

実際のセットアップは複数機能を組み合わせる。

| パターン               | 構成                                     | 例                                                                  |
| ---------------------- | ---------------------------------------- | ------------------------------------------------------------------- |
| **Skill + MCP**        | MCP が接続、Skill が使い方を教える       | MCP でデータベースに接続、Skill でスキーマとクエリパターンを文書化  |
| **Skill + Subagent**   | Skill が Subagent を起動して並列作業     | `/audit` Skill が security/performance/style の Subagent を並行起動 |
| **CLAUDE.md + Skills** | CLAUDE.md は常時ルール、Skill は参照資料 | CLAUDE.md に「API 規約に従え」、Skill に完全な API スタイルガイド   |
| **Hook + MCP**         | Hook が MCP 経由で外部アクション         | 編集後 Hook が Slack 通知を MCP 経由で送る                          |

## 10. コンテキストコスト（重要）

各機能は Claude のコンテキストウィンドウを消費する。**詰め込みすぎると逆効果**。

| 機能             | いつロード                                   | コスト                   |
| ---------------- | -------------------------------------------- | ------------------------ |
| **CLAUDE.md**    | セッション開始                               | 毎リクエスト（全文）     |
| **Skills**       | セッション開始（説明文のみ）+ 使用時（本文） | 低（説明文のみ常時）     |
| **MCP サーバー** | セッション開始（ツール名のみ）               | 低(使用時まで遅延ロード) |
| **Subagents**    | 起動時                                       | メインから隔離           |
| **Hooks**        | トリガー時                                   | ゼロ（外部実行）         |

### ハマりどころ

- CLAUDE.md が肥大化すると **Claude が指示を無視し始める**
- Skill の説明文が曖昧だと **Claude が間違った Skill をロードする**
- MCP サーバーが多すぎると **トークン消費が増える** → `/mcp` で確認

## 11. まとめ：1 枚で覚える

```
セッション開始
  ↓
[CLAUDE.md が自動ロード] ← 常時の規約
  ↓
[Skills の説明文がロード] ← 使うかもしれない知識
  ↓
[MCP のツール名がロード] ← 外部接続
  ↓
ユーザーがプロンプト
  ↓
必要に応じて：
  - Skill 本文をロード（自動 or /コマンド）
  - MCP ツール呼び出し
  - Subagent 起動（隔離コンテキスト）
  - Hook 発火（イベント時）
```

**核となる原則**：

1. 最初は CLAUDE.md だけ
2. 同じことを繰り返したら Skill 化
3. 外部接続が必要になったら MCP
4. コンテキストが汚れてきたら Subagent
5. 確実にやりたい処理は Hook
6. 複数プロジェクトで再利用したくなったら Plugin

# Part 3: Claude Code セッション管理：コンテキストの基本操作

Claude Code でコンテキスト（会話の文脈）を扱うための基本コマンド集。これを知らないと「PC再起動したら全部消えた」「会話が長くなって Claude がボケ始めた」「あの時の議論に戻りたいのに戻れない」という事態になる。

## 出典

- Anthropic 公式「Manage sessions」
  <https://code.claude.com/docs/en/sessions>
- Anthropic 公式「Work with sessions (Agent SDK)」
  <https://platform.claude.com/docs/en/agent-sdk/sessions>
- Anthropic 公式「Best practices for Claude Code」
  <https://code.claude.com/docs/en/best-practices>

## 結論：5つの基本動作を覚える

1. **続きから始める**（`--continue`、`--resume`）
2. **セッションに名前を付ける**（`/rename`）
3. **会話を分岐させる**（`/branch`）
4. **特定の地点に戻す**（`/rewind`、`Esc Esc`）
5. **コンテキストを整理する**（`/clear`、`/compact`、`/context`）

これだけ覚えておけば、Boris のような並列セッション運用も、長期プロジェクトの管理もできる。

## セッションとは何か

公式の定義：

> 「A session is a saved conversation tied to a project directory. Claude Code stores it locally as you work, so you can resume where you left off, branch to try a different approach, or switch between tasks.」
> （セッションはプロジェクトディレクトリに紐づいた保存済みの会話。Claude Code は作業中に自動でローカル保存するので、続きを再開、別アプローチへの分岐、タスク切り替えができる）

### 重要なポイント

- **自動保存される**：何も操作しなくても、会話は全部ローカルに残る
- **プロジェクトごとに管理**：ディレクトリが違えば別セッション
- **PC再起動しても消えない**：ローカルファイルに保存されているから

### 保存場所

```
~/.claude/projects/    ← プロジェクトごとのセッション履歴
~/.claude/history.jsonl ← 入力履歴
```

ホームディレクトリ配下なので、PCが壊れない限り消えない。

## 続きから始める

### `claude --continue`（短縮形 `claude -c`）

**そのディレクトリで最後にやっていた会話**を即座に復活させる。

```bash
cd ~/projects/my-app
claude --continue    # 昨日の続きから
```

「昨日の続きやろう」みたいなノリで使う。一番カジュアル。

### `claude --resume`（短縮形 `claude -r`）

**過去の会話の一覧**を出して、選択できる。

```bash
claude --resume
```

出てくる画面：

```
Past sessions in this directory:
  1. oauth-implementation (2 hours ago, 142 messages)
  2. fix-login-bug (yesterday, 38 messages, main)
  3. add-payment-flow (3 days ago, 91 messages, feature/payment)
```

各行に表示される情報：
- セッション名（命名済みの場合）または最初のプロンプト
- 最終アクティビティからの時間
- メッセージ数
- git ブランチ名

複数のタスクを並行している人向け。

### キーボードショートカット

セッションピッカー内で：

| キー | 動作 |
|---|---|
| `Ctrl+A` | 全プロジェクトのセッションを表示 |
| `Ctrl+B` | 現在の git ブランチでフィルタ |
| `R` | 選択中のセッションをその場で rename |
| `→` | フォークされたセッショングループを展開 |

### セッション中に切り替える

セッション内から `/resume` を打つと、**今のセッションを抜けずに別のセッションに切り替える**ピッカーが開く。

```
/resume
```

複数タスクを行き来する人にはこれが効く。

### セッション ID で直接指定

ID が分かっていれば一発：

```bash
claude --resume abc123def456
```

## セッションに名前を付ける（重要）

Anthropic 公式の強い推奨：

> 「Name sessions early: Use /rename when starting work on a distinct task — it's much easier to find 'payment-integration' than 'explain this function' later.」
> （セッションは早めに命名せよ。`/rename` で個別タスクに名前を付けると、後で「payment-integration」を見つけるのが「explain this function」を見つけるよりずっと簡単になる）

### `/rename` の使い方

セッション中に：

```
/rename oauth-migration
```

これでこのセッションに `oauth-migration` という名前が付く。後で：

```bash
claude --resume oauth-migration
```

で一発呼び出し。

### 命名のコツ

| 良い名前 | 悪い名前 |
|---|---|
| `payment-integration` | `explain this function` |
| `fix-auth-bug-2026-05` | `debugging` |
| `refactor-user-model` | `working` |

**「3日後の自分が見て、何のセッションか分かるか」**で判定。

### Boris の使い方

> 「セッションを `/rename` で名付けて、ブランチのように扱う。各ワークストリームが自分の永続的なコンテキストを持つ」

つまり**「セッション = git ブランチ」**の発想。`feature-auth`、`bugfix-login`、`refactor-db` みたいに付けて並行運用する。

## 会話を分岐させる（`/branch`）

公式の説明：

> 「Branching creates a copy of the conversation so far and switches you into it, leaving the original intact. Use it to try a different approach without losing the path you were on.」
> （ブランチは今までの会話のコピーを作って、そちらに切り替える。元のセッションはそのまま残る。今の道を失わずに別アプローチを試すために使う）

### 使い方

セッション中に：

```
/branch try-different-approach
```

これで会話が分岐する。元のセッションは無傷で残り、新しい分岐に移動する。

### 動作の確認

`/branch` を実行すると、確認画面に **2 つのセッション ID** が表示される：
- 新しい分岐のID（今いる場所）
- 元のセッションのID

### 元のセッションに戻る方法

3 つの方法：
1. `claude --resume <元の名前>` で名前指定
2. `claude --resume <元のID>` で ID 指定
3. セッションピッカーで選ぶ

### 注意点

- セッション内で許可した「このセッション中は許可」のパーミッションは、**新しい分岐には引き継がれない**
- フォークされたセッションは、ピッカーで**元のセッションの下にグループ化**される（`→` で展開）

### 何の役に立つか

例：「リファクタの方針A と方針B を両方試したい」

```
[元のセッション]
コードのリファクタを議論中
   ↓
/branch refactor-strategy-a
   ↓ 方針A を実装させる
   ↓ 結果を見る → 微妙
   ↓
claude --resume <元のセッション>
   ↓
/branch refactor-strategy-b
   ↓ 方針B を実装させる
   ↓ こっちが良い → 採用
```

両方が独立したセッションとして残るので、後から比較できる。

### CLI からフォーク

セッションを開かずに、コマンドラインで分岐：

```bash
claude --resume <session-id> --fork-session
```

## 特定の地点に戻す（`/rewind`）

公式の説明：

> 「The `/rewind` command (also triggered by `Esc+Esc`) jumps back to a previous message state.」

セッション中の特定の地点に戻る機能。

### 使い方

セッション中に：

```
/rewind
```

または `Esc` を 2 回押す。

すると、過去のメッセージ一覧が表示されて、戻りたい地点を選べる。

### 戻り方の選択肢（5種類）

戻る地点を選んだ後、何を戻すかを選ぶ：

| 選択肢 | 動作 |
|---|---|
| **Rewind conversation** | 会話だけ戻す（コードはそのまま） |
| **Rewind code** | コードだけ戻す（会話はそのまま） |
| **Rewind both** | 両方戻す（完全に巻き戻し） |
| **Summarize from here** | この地点以降を要約する（コンテキスト節約） |
| **Branch from here** | この地点から分岐させる |

### 「Summarize from here」が地味に強い

`/compact` はセッション全体を要約するが、`Summarize from here` は **特定地点以降だけを要約**できる。

「最初の議論は重要だから残したい、でも途中の試行錯誤は要約していい」みたいな時に効く。

### `Esc` の 2 種類の使い方

- **1回押し**：Claude の応答中に押すと、生成を止める。コンテキストは保持される
- **2回連続**：rewind ピッカーを開く

### チェックポイント機能

公式：

> 「Checkpoints persist across sessions, so you can rewind even after closing the terminal.」
> （チェックポイントはセッションをまたいで永続する。ターミナルを閉じても後で巻き戻せる）

つまり、PC再起動後でも「あの時点に戻りたい」ができる。

## コンテキストを整理する

セッションが長くなってきた時のメンテナンス系コマンド。

### `/clear` — 完全リセット

今のコンテキストを全部消して、まっさらにする。

```
/clear
```

公式の説明：

> 「/clear: start fresh with an empty context. The previous conversation is saved and resumable」
> （/clear: 空のコンテキストで再スタート。前の会話は保存されており、再開可能）

ポイント：
- ✅ **コードの変更はそのまま残る**（会話履歴だけ消える）
- ✅ 前のセッションはピッカーから再開できる
- ✅ 全く別のタスクに移る時に使う

### `/compact` — 賢く要約

会話を要約して圧縮する。Claude が「重要そうな情報」を判断して残す。

```
/compact
```

ヒント付きで指定もできる：

```
/compact 修正したファイルのリストとテストコマンドは必ず残して
```

公式の推奨：

> 「Always use proactive /compact with explicit hints rather than waiting for autocompaction on complex tasks. Autocompaction is a safety net, not a strategy.」
> （複雑なタスクでは、自動圧縮を待つのではなく、明示的なヒント付きで `/compact` を積極的に使え。自動圧縮はセーフティネットであって戦略ではない）

つまり、**自動圧縮が走る前に、自分で適切なヒント付きで圧縮**するのが正解。

### `/context` — 何が入っているか確認

今のコンテキストに何が入っているかを表示する。

```
/context
```

これで「あ、CLAUDE.md が肥大化してる」「使ってない MCP のツール定義が大量に乗ってる」などが分かる。

### 使い分け早見表

| 状況 | コマンド |
|---|---|
| 全く別のタスクに移る | `/clear` |
| 同じタスクだが長くなった | `/compact <ヒント>` |
| 何がコンテキストを食っているか確認 | `/context` |
| 特定の時点までの履歴だけ要約 | `/rewind` → Summarize from here |

## 全コマンド早見表

これだけは覚えておくべき一覧：

| コマンド | 動作 |
|---|---|
| `claude` | 新規セッション開始 |
| `claude --continue` (`-c`) | 直前の会話を続ける |
| `claude --resume` (`-r`) | 過去の会話ピッカーを開く |
| `claude --resume <名前>` | 名前指定で直接再開 |
| `claude --resume <id> --fork-session` | CLI からフォーク |
| `/resume` | セッション中に切り替えピッカー |
| `/rename <名前>` | セッションに名前を付ける |
| `/branch <名前>` | 会話を分岐させる |
| `/rewind` または `Esc Esc` | 過去の地点に戻る |
| `/clear` | コンテキスト全クリア（会話保存） |
| `/compact <ヒント>` | コンテキストを要約 |
| `/context` | コンテキスト消費状況を表示 |

## 実践パターン

### パターン 1：朝の作業開始

```bash
cd ~/projects/my-app
claude --continue    # 昨日の続きから
```

### パターン 2：複数タスクの並列運用（Boris 流）

```bash
# ターミナルタブ1
cd ~/projects/my-app
claude --resume oauth-migration

# ターミナルタブ2
cd ~/projects/my-app
claude --resume bugfix-login

# ターミナルタブ3
cd ~/projects/my-app
claude --resume refactor-db
```

各タブが独立したコンテキストで動く。

### パターン 3：新しいタスクを始める時

```
# 既存セッション中で別タスクに移る場合
/clear
   ↓ 新しいタスクの説明
/rename new-feature-payment    ← 早めに名付け
```

### パターン 4：危険な実験

```
[現在のセッション]
   ↓ 「この機能、リスキーだけど試したい」
/branch risky-experiment
   ↓ 実験する
   ↓ 失敗 → 捨てる
   ↓
claude --resume <元のセッション>    ← 元の状態に戻る
```

### パターン 5：長くなりすぎたセッション

```
[セッションが長い]
   ↓
/context    ← まず状況確認
   ↓ 「CLAUDE.md が大きすぎる」「Skill が多すぎる」など発見
   ↓
/compact 進行中の認証実装の決定事項とテスト結果は必ず残して
   ↓ コンテキスト整理完了
```

### パターン 6：Claude が変な方向に進んだ

```
[Claude が間違った方向で実装中]
   ↓
Esc Esc    ← rewind ピッカー
   ↓ 間違いの直前のメッセージを選択
   ↓ "Rewind both" を選択
   ↓ コードも会話も巻き戻し
   ↓ 正しい指示を入れ直す
```

### パターン 7：git worktree との組み合わせ

公式の推奨：

> 「Combining this with Git Worktrees makes session management even more powerful.」

```bash
# Worktree 1 で機能開発
cd ../my-project-feature-a
claude --continue

# Worktree 2 でバグ修正（別ターミナル）
cd ../my-project-bugfix
claude --continue
```

Worktree ごとに独立したセッションが維持される。

## ベストプラクティス

### 公式から導かれる推奨事項

1. **セッションは早めに命名する** — タスクを始めた瞬間に `/rename`
2. **タスクごとにセッションを分ける** — 1つの巨大セッションより、複数の小さいセッション
3. **`/compact` は自分でヒント付きで** — 自動圧縮を待たない
4. **危険な実験は `/branch` で** — 元のセッションを守る
5. **間違ったら `/rewind`** — 修正指示を重ねるよりロールバック
6. **新タスクは `/clear` で** — コンテキスト汚染を防ぐ

### Boris の運用ルール

| やること | 理由 |
|---|---|
| 毎セッションに名前を付ける | 後で探せる |
| ターミナル5タブ + Web 5-10セッションを常時稼働 | 並列でスループット最大化 |
| 各タブは別の git checkout | コンテキストが混ざらない |
| 通知でどのセッションが入力待ちか把握 | 効率的にコンテキストスイッチ |

## デスクトップアプリ・Web版との違い

公式の明記：

> 「The desktop app, Claude Code on the web, and the VS Code extension each maintain their own session history.」
> （デスクトップアプリ、Web版、VS Code 拡張は、それぞれ独自のセッション履歴を持つ）

つまり：

- **Claude Code CLI のセッション**：ローカルに保存（`~/.claude/`）
- **Claude.ai のチャット**：クラウド保存（ブラウザの履歴）
- **Claude Code on the web**：クラウド保存
- **VS Code 拡張**：別管理

これらは**相互に連動しない**。CLI でやった会話は Web には出てこないし、逆も同じ。

## セッションファイルを直接いじる（上級）

セッションは JSON Lines 形式でローカルに保存されている：

```bash
~/.claude/projects/<プロジェクトパスのエンコード版>/<session-id>.jsonl
```

### バックアップ

大事なセッションをバックアップしたい場合：

```bash
cp ~/.claude/projects/-Users-you-Code-project/SESSION_ID.jsonl ~/backups/
```

### 削除

完全に消したいセッションがある場合：

```bash
rm ~/.claude/projects/-Users-you-Code-project/SESSION_ID.jsonl
```

### 完全リセット（核オプション）

全部消す。**取り返しがつかないので注意**：

```bash
rm ~/.claude/history.jsonl
rm -rf ~/.claude/projects/*/
```

## まとめ：5つの原則

1. **セッションは消えない**：PC再起動しても残る
2. **名前を付ける**：後で探せるように `/rename` を癖にする
3. **分岐できる**：危険な道は `/branch` で別経路を作る
4. **戻せる**：間違ったら `/rewind` で巻き戻す
5. **整理する**：長くなったら `/compact <ヒント>`、別タスクなら `/clear`

これでコンテキスト管理は怖くなくなる。
